# Olist 电商分析项目：业务需求说明书

## 1. 项目定位

本项目面向数据分析岗位作品集，使用 Olist Brazilian E-Commerce Public Dataset，模拟电商平台分析师为管理层、增长团队和履约团队提供经营诊断与决策建议的工作场景。

项目不以“罗列图表”为目标，而围绕一条可复述的业务主线展开：

> 经营表现发生了什么变化？变化由哪些客户、品类、地区和订单因素驱动？客户是否持续回来购买？履约体验是否与评价相关？下一步应通过什么实验验证改进方案？

## 2. 数据背景与边界

- 数据源：Olist 在 Kaggle 发布的 Brazilian E-Commerce Public Dataset。
- 数据规模：约 10 万笔订单，覆盖 2016—2018 年。
- 主要主题：订单、订单商品、支付、客户、卖家、商品、评价、履约时间和地理位置。
- 客户识别：`customer_id` 是订单级客户键；跨订单识别同一客户必须使用 `customer_unique_id`。
- 数据为历史、匿名、观察性数据，不能直接证明因果关系。

### 2.1 可以回答的问题

- GMV、订单量、AOV、购买客户数如何随时间变化？
- GMV 变化由订单量还是客单价驱动？进一步由购买客户数、购买频次、件单量或商品均价中的哪一项驱动？
- 哪些州、城市、品类、卖家和支付方式贡献主要业绩或异常波动？
- 新客户在首购后的留存和复购表现如何？哪些客户属于高价值或流失风险群体？
- 配送时长、晚到与评价分数之间是否存在统计关联？
- 针对履约或复购问题，可以设计怎样的 A/B Test？

### 2.2 不能直接回答的问题

由于缺少曝光、访问、加购、营销成本、折扣、商品成本和明确退货记录，本项目不计算或不宣称：

- 流量转化率、加购转化率；
- 毛利、净利润、ROI、CAC；
- 真实退货率；
- 某项运营动作对 GMV 或评分的因果影响；
- 基于人口属性的用户画像。

## 3. 业务目标与分析模块

### 目标 A：经营概览与趋势诊断

**业务问题**

1. 月度经营表现如何，增长或下滑出现在哪些时期？
2. 波动主要来自订单量、AOV 还是活跃购买客户数？
3. 哪些地区、品类和卖家贡献了变化？

**分析方法**

- 同比仅在存在可比完整月份时使用；主要采用环比、移动平均和贡献度分析。
- 使用窗口函数计算环比、累计值、排名和贡献率。
- 使用以下拆解关系：
  - `GMV = 订单量 × AOV`
  - `订单量 = 购买客户数 × 人均订单数`
  - `AOV = 件单量 × 商品均价`
- 对异常月份按州、品类、卖家、订单状态和支付方式下钻。

**交付物**

- Power BI 经营总览页与趋势诊断页；
- SQL 月度经营指标集市、趋势拆解和下钻查询；
- 3—5 条有数据证据、带业务影响的结论。

### 目标 B：客户留存与价值分层

**业务问题**

1. 各首购月 Cohort 的后续月留存率如何？
2. 复购客户占比是多少，复购间隔有何特征？
3. 哪些客户应被识别为高价值、潜力、需唤醒或流失客户？

**分析方法**

- 使用 `customer_unique_id` 作为客户实体。
- 首次成功购买月份定义为 Cohort 月；第 0 月为首购月。
- 月留存率定义为：Cohort 在第 N 月仍有成功购买的客户数 / Cohort 首购客户数。
- 同时报告全周期复购率和固定观察窗复购率，避免较晚 Cohort 因观察期较短而被低估。
- RFM 使用统一分析快照日，基于成功订单计算 Recency、Frequency、Monetary，并记录分层规则。

**交付物**

- Cohort 留存矩阵与留存曲线；
- 复购率、复购间隔分布；
- RFM 客户明细、分层汇总及运营建议；
- Power BI 用户分析页。

### 目标 C：履约体验与评价诊断

**业务问题**

1. 配送用时和晚到率如何变化？哪些地区、品类或卖家表现异常？
2. 晚到订单与准时订单的评价分数是否存在显著差异？
3. 配送时长与评价分数的关联强度有多大，结果是否具有业务意义？

**分析方法**

- 配送时长：`order_delivered_customer_date - order_purchase_timestamp`。
- 晚到：实际送达日期晚于预计送达日期。
- 描述统计同时报告均值、中位数、分位数和样本量。
- 对评分差异给出置信区间、假设检验、效应量；根据分布和稳健性需要选择 Welch t 检验和/或非参数检验。
- 相关分析区分统计相关与因果结论，并考虑订单时间、地区、品类等潜在混杂因素。

**交付物**

- Python 可复现统计分析；
- 配送表现和评分诊断页；
- 统计显著性、效应大小、局限性和业务解释。

### 目标 D：A/B Test 方案设计

根据前述分析选择一个明确的干预场景，例如“对预计延迟订单发送主动通知及补偿券”，完成实验方案，不伪造实验结果。

方案至少包括：

- 业务假设、实验单位、随机化方式和目标人群；
- 一个主指标、必要的次要指标和护栏指标；
- 基线值、最小可检测效应（MDE）、显著性水平、检验功效和样本量；
- 实验周期、污染风险、多重检验及提前停止规则；
- 统计显著性、效应量与商业收益的联合决策框架。

## 4. 核心指标口径

为避免支付表和商品表的一对多连接造成重复计算，GMV、运费和支付额分别在订单粒度预聚合后再连接。

| 指标 | 主口径 | 补充说明 |
|---|---|---|
| 成功订单 | `order_status = 'delivered'` 的去重 `order_id` | 主看板统一使用；其他状态单独展示 |
| GMV | 成功订单中 `SUM(order_items.price)` | 表示商品成交额，不含运费；不是利润 |
| 含运费成交额 | `SUM(price + freight_value)` | 作为补充指标，不能与 GMV 混用 |
| 支付额 | 订单级聚合后的 `SUM(payment_value)` | 用于支付分析和口径核对，不替代商品 GMV |
| 订单量 | 成功订单的 `COUNT(DISTINCT order_id)` | 避免订单商品行导致重复 |
| AOV | `GMV / 成功订单量` | 分母为成功订单 |
| 购买客户数 | 成功订单的 `COUNT(DISTINCT customer_unique_id)` | 不使用 `customer_id` 计算人数 |
| 人均订单数 | `成功订单量 / 购买客户数` | 与 AOV 一起解释 GMV |
| 件单量 | `成功商品件数 / 成功订单量` | 每个订单商品行视为一件；需在数据验证阶段确认 |
| 商品均价 | `GMV / 成功商品件数` | 不含运费 |
| 全周期复购率 | 有至少 2 笔成功订单的客户数 / 有至少 1 笔成功订单的客户数 | 会受右删失影响 |
| 固定窗复购率 | 首购后指定天数内再次成功购买的客户数 / 拥有完整观察窗的首购客户数 | 计划同时计算 90 天口径 |
| 月留存率 | Cohort 第 N 月购买客户数 / Cohort 第 0 月客户数 | N 为自然月差 |
| 晚到率 | 晚到且已送达订单数 / 同时有实际和预计送达日期的已送达订单数 | 缺失日期不进入分母 |
| 平均评价分 | 有评价订单的 `AVG(review_score)` | 同时展示分布和有效样本量 |

## 5. 时间与数据处理原则

- 趋势归属日期统一使用 `order_purchase_timestamp`。
- 月度趋势只比较完整自然月；数据首尾不完整月份单独标记或排除。
- 时间戳统一转换为同一时区/无时区口径，本项目不进行跨时区换算。
- 缺失值不默认填零；每个派生指标明确有效样本和排除规则。
- 城市名称、品类翻译、邮编前缀和重复地理坐标在清洗层处理。
- 金额计算保留高精度数值类型，展示层再四舍五入。
- 所有核心指标必须通过订单粒度对账，防止一对多 JOIN 放大金额。

## 6. Power BI 使用场景

计划设计 4 个页面：

1. **Executive Overview**：GMV、订单量、AOV、客户数、复购率和关键趋势。
2. **Performance Diagnosis**：指标拆解、月度变化贡献、地区/品类/卖家下钻。
3. **Customer Analytics**：Cohort、Retention、RFM 分层和复购行为。
4. **Delivery & Reviews**：配送时长、晚到率、评价分与统计结论摘要。

通用交互包括日期、州、品类筛选，跨图表联动，Tooltip 明细，以及从总览到地区/品类的 Drill-through。Dashboard 使用预建指标集市或星型模型，避免直接将原始多对多关系交给报表层。

## 7. 项目验收标准

### SQL

- 展示多表 JOIN、CTE、窗口函数、条件聚合和日期处理；
- 建立 raw/staging/core/mart 分层或等价的清晰建模流程；
- 每张核心表包含粒度、主键和字段说明；
- 包含行数、唯一性、空值、引用完整性和金额对账测试；
- 核心指标可由独立 SQL 查询复算。

### Python

- 代码从 SQL 导出的分析数据集开始，可一键复现；
- 报告描述统计、置信区间、假设检验、效应量和相关分析；
- 检查检验假设并说明替代方法；
- A/B Test 样本量参数透明、可调整，结论包含商业判断。

### Power BI

- 口径与 SQL 指标字典一致；
- 至少包含趋势、拆解、下钻、Cohort/RFM 和履约体验页面；
- 图表标题、单位、筛选状态和数据截止日期清楚；
- 仓库保存 `.pbix` 文件（如体积许可）、页面截图和指标说明。

### GitHub 作品集

- README 能在 2—3 分钟内说明背景、问题、方法、洞察和建议；
- 提供数据获取方式，不提交不必要的大型原始数据；
- 提供运行顺序、依赖、数据模型图和关键截图；
- 每条结论可追溯到 SQL/Python 代码和明确指标口径；
- 不把观察性相关描述为因果，不展示无法由数据支持的指标。

## 8. 预期业务结论模板

最终结论统一采用以下结构：

1. **现象**：指标在何时、何处变化，幅度多大；
2. **定位**：由哪个拆解项、客户群、地区或品类贡献；
3. **证据**：样本量、对比基准、统计不确定性；
4. **行动**：建议采取何种运营或产品动作；
5. **验证**：如何通过后续指标监控或 A/B Test 验证。
